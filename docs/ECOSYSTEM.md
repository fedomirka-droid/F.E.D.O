# F.E.D.O. Ecosystem — Personal Edition

Редакция для одного владельца, построенная **поверх** существующего
F.E.D.O. Core v1.5.x. Core не переписан: его монитор, личности, prompt-ы и
команды используются через `ecosystem/backend/services/core_bridge.py`.

## Компоненты

```
┌────────────────────┐        HTTPS + HMAC        ┌──────────────────────┐
│ F.E.D.O. Desktop   │ ───────── sync ─────────▶  │   F.E.D.O. HUB       │
│ Tauri 2 + React    │ ◀──────── pull ──────────  │   FastAPI + SQLite   │
│ локальный backend  │                            │   VPS (Ubuntu 24.04) │
│ SQLite + outbox    │                            └──────────┬───────────┘
└─────────┬──────────┘                                       │
          │ разрешённые команды (подпись канала)             │ bot API
          ▼                                                  ▼
┌────────────────────┐                              ┌────────────────────┐
│ F.E.D.O. GPU Core  │  AI-шлюз /api/ai/chat         │  F.E.D.O. Mini    │
│ домашний ПК RTX3080│◀──── AI Router (remote_node) ─│  Aiogram 3 бот    │
│ Agent + LM Studio  │                              │  (без своей БД)   │
└────────────────────┘                              └────────────────────┘
```

### Desktop
Отдельное окно Tauri 2, локальный Python-backend как sidecar, работа без
интернета, локальная SQLite, очередь изменений, 8 разделов интерфейса.

### HUB
Центральный сервер: авторизация, привязка устройств, синхронизация,
уведомления, API для Desktop и Telegram, маршрутизация разрешённых команд.
HUB **не обязателен** для локальной работы Desktop.

### Mini
Telegram-бот Aiogram 3. Не хранит собственных задач: все запросы идут в HUB
с сервисным токеном. Привязка — одноразовый код из Desktop.

### GPU Core
Обычный Desktop + AI-шлюз, отдающий локальную модель ноутбуку и Telegram.

## Модель данных синхронизации

| Поле | Назначение |
|------|------------|
| `id` (UUID) | глобально уникальный идентификатор |
| `owner_id` | владелец (готовность к мультиарендности) |
| `version` | монотонная версия записи |
| `updated_at` (UTC) | время изменения |
| `deleted_at` | tombstone (мягкое удаление) |
| `origin_device` | устройство-источник последней правки |
| `op_id` | идемпотентность операций в `sync_operations` |

Что синхронизируется: задачи, события календаря, расписание, статусы,
разрешённые пользовательские предпочтения.
Что **не** синхронизируется: история диалогов, API-ключи, локальные файлы.

### Алгоритм

1. Desktop пишет локально → запись в `outbox` (схлопывание повторов по сущности).
2. Push `POST /api/sync/push` с `base_version`.
3. HUB применяет, если `base_version == version`; иначе — конфликт.
4. Ответ `applied` → outbox очищается, локальная версия берётся с сервера.
5. `GET /api/sync/pull?cursor=N` отдаёт `change_log` после курсора,
   исключая изменения собственного устройства.
6. Повторы не создают дублей (сравнение содержимого + журнал операций).
7. Ошибки → экспоненциальный backoff (5s → 300s), очередь переживает перезапуск.

### Конфликты

При несовпадении версии HUB **не перезаписывает** данные, а сохраняет обе
версии в `sync_conflicts`. Владелец в UI (Настройки → Конфликты) выбирает:
«принять мою» или «оставить серверную». Last Write Wins не применяется.

## AI Router 2.0

Режимы: `local_only`, `hybrid`, `cloud_preferred`, `manual`.

Порядок кандидатов в `hybrid`: локальная модель → домашний AI-узел → облако.
Проверки **перед каждым облачным запросом**:

* `allow_cloud = false` → облако запрещено полностью, никакой fallback не обходит;
* дневной лимит запросов и месячный бюджет;
* `allow_history_to_cloud = false` → в облако уходит только текущий запрос;
* ключи хранятся зашифрованными (Fernet) и маскируются в логах.

Дополнительно: таймауты, отмена (по `request_id`), SSE-стриминг,
учёт токенов/стоимости, трассировка маршрута в ответе.

Локальные команды Core (имя, профиль, «состояние системы») отвечают без сети.
Команды с побочными действиями (`открой браузер`, `проводник`) через Router
**не проходят** — только явные кнопки Desktop.

## Безопасность

* пароли — scrypt с солью; сессии — opaque-токены, в БД только SHA-256;
* отдельные токены устройств + HMAC-секрет канала (шифруется Fernet);
* rate limit на login/setup/API и на попытки привязки Telegram;
* CORS-allowlist, CSP в Tauri, ограничение размера загрузок;
* журнал аудита всех операций управления устройствами;
* команды устройств — строго типизированный белый список, опасные требуют подтверждения;
* запрещено: произвольный shell, незащищённый API в интернет, секреты в Git.

## Роли процесса

`FEDO_ROLE=hub` — синхронизация, Telegram, API.
`FEDO_ROLE=desktop` — локальная работа + очередь изменений + опциональный sync.

Один и тот же код, два режима.
