## Что СДЕЛАНО вместо «имитации интеграции»

1. **Модель профиля студента** (`student_profiles`): группа, колледж, специальность,
   курс, семестр, форма обучения, зачётка, заметки. Синхронизируется между устройствами
   (сущность `student_profile` в Sync Engine) и доступна через API.
2. **Сканер исходников** `services/student.detect_legacy()` — ищет артефакты и
   возвращает точный список найденного/отсутствующего (см. таблицу «Ожидаемые файлы»).
   Сканер отсекает собственные базы Ecosystem, чтобы не «импортировать» пользователю
   его же задачи.
3. **Реальный импортёр** `services/student.import_legacy()` — читает **чужую** SQLite-базу
   Student Edition (read-only), переносит задачи, расписание и профиль:
   * идемпотентен: id считается через `uuid5` от содержимого, поэтому повторный импорт
     обновляет, а не дублирует;
   * понимает разные имена колонок (`name/title`, `deadline/due_date`, `prio/priority` …);
   * нормализует статусы (`doing → in_progress`, `completed → done`, `cancelled → skipped`);
   * поддерживает `dry_run` — показать, что было бы импортировано, ничего не записав;
   * не создаёт второго владельца: пользователи legacy-базы только сопоставляются.
4. **Тесты** (`tests/test_ecosystem_integration.py`): импорт на синтетической legacy-базе,
   идемпотентность, `dry_run`, отказ на не-SQLite файле, отказ на собственной базе
   Ecosystem, обнаружение базы, «профиль уезжает на HUB через sync».

Проверено на синтетической базе, повторяющей чужую схему:

```
tasks: 3 строки (включая дубль)  → импортировано 2 задачи, дубль схлопнут
lessons: 2 строки                → 2 занятия с датой, преподавателем, кабинетом
student_profile: 1 строка        → профиль обновлён, source = legacy_import
users: 1 строка ('owner')        → сопоставлен с владельцем, второй не создан
повторный импорт                 → created: 0, дубликатов нет
```

Если данных достаточно только в виде БД — интеграция выполняется по шагам:

```bash
# 1) проверить, что система видит источник
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8765/api/student/status | jq

# 2) «сухой прогон» — ничего не записывая
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
     -d '{"path": "/path/to/student_edition.db", "dry_run": true}' \
     http://127.0.0.1:8765/api/student/import | jq

# 3) боевой импорт
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
     -d '{"path": "/path/to/student_edition.db"}' \
     http://127.0.0.1:8765/api/student/import | jq
```

## Если вернут исходники (а не только базу)

1. Положить каталог в корень, проверить `GET /api/student/status` → `adapter_ready`.
2. Сопоставить поля в `LEGACY_SCHEMAS` (`services/student.py`): `TASK_FIELD_ALIASES`,
   `SCHEDULE_FIELD_ALIASES`, `PROFILE_FIELD_ALIASES` — это единственное место правок.
3. Запустить импорт в `dry_run`, сравнить, затем боевой.
4. Перенести уникальные экраны в `desktop/src/pages` (сейчас 8 разделов закрывают
   профиль, задачи, расписание, AI, устройства, настройки).
5. Прогнать `pytest -q` (тесты интеграции уже готовы и покроют регрессии).

## Что НЕ будет сделано без исходников

* Перенос специфических студенческих функций Student Edition, которых нет в описании
  (например собственные отчёты, зачётная книжка, специфичные для MVP экраны).
* Точное совпадение схемы URL/ответов Student Edition (контракт неизвестен).
* Миграция пользователей Student Edition (их модель пользователей не видна).

Эти пункты остаются открытыми осознанно: лучше зафиксировать пробел, чем объявить
несуществующую интеграцию выполненной.
